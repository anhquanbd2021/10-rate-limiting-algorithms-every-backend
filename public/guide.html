Mechanics guide

Every limiter in the lab is a stateful function that takes an injected clock (now in ms) and returns allow/deny. Ten names on the listicle collapse into four real mechanisms, one different axis, and some knobs.

Boundary lab — windows are clocks, and clocks have edges

fixedWindow keeps one counter per clock-aligned window and resets on rollover. That is the whole mechanism — and the whole bug: requests at the end of window N and the start of window N+1 are never compared, so a burst packed against the edge admits up to 2× the quota inside a span much shorter than the window.

The sliding variants: slidingWindow keeps two counters and weights the previous window by how much of it is still inside the rolling span — O(1) memory, approximate (it assumes the old traffic was spread evenly). slidingLog stores one timestamp per request and prunes — exact, at O(n) memory and an O(n) scan per call. In the lab stream both hold the edge burst to the limit where fixed doubles it.

Buckets lab — rate and burst are different dials

tokenBucket refills tokens at ratePerSec up to capacity; a request costs tokens. Capacity banked during idle is what lets a burst through — "burst allowance" is this parameter, not a separate algorithm. The emission shape is the input shape: whatever you admit, you admit instantly.

Leaky is the opposite product: leakyBucket is a metered queue — requests enter (up to capacity) and exit at exactly the drain rate. The lab emits an idle request immediately, then spaces the backlog by the interval: 8 requests in 70ms come out at a perfect 500ms cadence over 3.5s. Use it to protect a jitter-sensitive downstream, not to "limit" — it trades latency for smoothness.

Concurrency lab — in-flight is a different axis

concurrency counts requests currently holding a slot, each released after holdMs. Per-second limiters are blind here: six requests that each occupy a slot for five seconds are a trivial rate and a total exhaustion. The lab's six slow clients fill all four slots and four legitimate short requests are rejected — while the same stream passes a generous 10/s fixed window untouched.

The pairing rule: rate limits answer "how often," concurrency limits answer "how many at once." You need both — a rate limiter never sees held connections, and a concurrency cap never sees a fast hammer.

Deployment & clients lab — policy, state, behavior

Distributed counter is the same counters with hard state: two nodes each running "limit 10" admit 20 between them unless the counter is shared and atomic (a Redis INCR+expire, or a Lua script when the check must be read-modify-write). Clock skew between nodes is the second failure.

Per-user quota is a policy: wrap any mechanism in a key→limiter map. It stops the noisy neighbor — but one limiter per identity is a memory bill that scales with your key cardinality, and unbounded maps are their own attack.

Backoff is client-side. The server 429s; the client's retry schedule decides whether rejections become a storm. Eight clients retrying every 200ms generate 152 hits during a 4s outage; exponential backoff capped and jittered cuts that to 46 — Retry-After is the server asking nicely.

Honest limits

  • Single-node, in-memory, deterministic-clock models — no Redis, no network, no real clock skew beyond the scripted kind.
  • The "distributed counter" lab simulates shared state vs per-node state; it does not run an atomic store or model its latency/failure modes.
  • Sliding-window counter uses the standard weighted estimate — real implementations vary (and some track per-key last windows).
  • The leaky bucket models a metered queue with immediate emit when idle; GCRA-style variants make different trade-offs.
  • Backoff jitter uses a deterministic demo hash, not randomness — repeatability beats realism here.
